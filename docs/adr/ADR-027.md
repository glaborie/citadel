# ADR-027: Every worker and tool service verifies the run token and binds the payload to its claims

**Status:** Accepted
**Date:** 2026-11-27
**Last modified:** 2026-11-27
**Closes:** issue #237 (security audit)

## Context

Architecture §3.3 requires that every downstream component verify the delegated
run token, and §3.4 that tool calls carry it. The code satisfied this only at
the edges:

- `authorize_tool` and `execute_tool` built the `AuthorizationRequest` and the
  audit ledger entries from plain Temporal payload fields. Temporal does not
  authenticate whoever starts a workflow, so a peer on the `internal` network
  could start a `SpecialistWorkflow` whose fields name another tenant, another
  user and another run, and the policy decision, the pending-approval row and
  the `tool.call` event would be written into that tenant's hash chain under an
  impersonated subject.
- The runner compared only the `agent` claim; its request carried no
  `tenant_id`/`run_id`, so a leaked token for one run was spendable on any
  request the agent claim fitted.
- The operator took no credential at all: `tenant_id` came from the request
  body, so any peer on `internal` could drive the only component that performs
  a T1 write (subject to holding an unconsumed `approval_ref`, which travels in
  Temporal history).
- Workers received `CITADEL_RUN_TOKEN_PUBLIC_KEY` in their environment without
  any code reading it.

Alternatives considered:

- **Authenticate workflow starters at Temporal (mTLS or a Temporal namespace
  API key).** The right long-term boundary for the whole frontend (issue #238),
  but it does not make the payload trustworthy to the activities themselves,
  and v0.1 ships no Temporal auth plugin. Layered defence still requires the
  activities to refuse an unproven identity.
- **Let the worker trust the payload and have only the runner/operator verify.**
  Rejected: the ledger writes happen in the worker. A forged `policy.decision`
  or a pending approval row lands before any tool service is reached, so the
  forgery the audit exists to prevent would already have happened.

## Decision

1. **The worker verifies.** Both `authorize_tool` and `execute_tool` verify
   `call.run_token` with `CITADEL_RUN_TOKEN_PUBLIC_KEY` and refuse, before any
   other work, with a fail-closed rule ladder: `identity.token_missing`,
   `identity.token_unverifiable` (deployment fault), `identity.token_invalid`
   (signature, expiry, shape) and `identity.token_mismatch` (claims disagree
   with the payload's tenant, user, run or agent). `execute_tool` re-checks
   because activities are schedulable directly from the task queue, skipping
   the authorisation step entirely.
2. **An identity refusal writes nothing.** The `policy.decision` event this
   path used to append takes its tenant and subject from the payload - writing
   it would be the very forgery the check stops. The refusal is returned to the
   workflow as its result (the trajectory keeps it) and counted in
   `policy_denial_total`; no ledger event, no span, no idempotency row.
3. **Claims bound at the services.** The runner's `ExecuteRequest` now carries
   `tenant_id` and `run_id` and refuses a body that disagrees with the token
   (403). The operator requires the run token on every `/execute` (401 without
   it), takes the tenant only from its claims, and refuses a body whose
   `run_id` differs (403); `tenant_id` is no longer part of its request schema,
   so it cannot be supplied at all. The runner and the operator share one
   bearer dependency (`citadel.identity.bearer`) so the refusal order and
   status codes cannot drift.
4. **The mint TTL covers the approval wait.** The API mints with
   `max(DEFAULT_TTL_SECONDS, CITADEL_APPROVAL_TTL_SECONDS + 120s)`: a T1 call
   parks for the whole approval TTL between authorisation and the write, and
   every service now verifies the token at execution time. The 120-second
   margin covers the executor's own window; a token past its expiry refuses,
   it never extends. `CITADEL_APPROVAL_TTL_SECONDS` is already set on the API
   service, so the two numbers cannot drift apart.
5. **Red-team cases.** RT-AUTHZ-08 (workflow started with another tenant's
   fields and a foreign token is denied before any ledger write) and
   RT-AUTHZ-09 (operator `/execute` without a token is 401) join the pack.

## Consequences

- **Pros**: the identity reaching `authorize()`, the idempotency row, the
  approval console and the ledger is the token's, on every path, including
  direct activity scheduling; a leaked token is bound to one (tenant, run,
  agent) triple; the operator stops being an unauthenticated writer; the
  compose file's worker-only public key finally has a reader.
- **Cons**: a late identity failure surfaces as a workflow deny instead of a
  tool result, which changes observable rule ids (`identity.*` instead of
  `tool.refused`); a token that expires mid-run now fails inside the worker
  where the runner would have failed it anyway - the deadline was already
  real, only its enforcement point moved; the mint TTL is bounded below by the
  approval wait, so a deployment that raises `CITADEL_APPROVAL_TTL_SECONDS`
  lengthens its run tokens proportionally.
- **Out of scope, unchanged**: Temporal still does not authenticate workflow
  starters, so a peer holding a valid token for a run can replay that run's own
  payload until the token expires - the same class of residual risk ADR-024
  accepts for approval references. Closing it needs the frontend boundary of
  issue #238. `RunActivities.finish_run` takes no credential either and shares
  the payload-trust assumption; it writes only `run.end` status events and is
  left as recorded follow-up work.
