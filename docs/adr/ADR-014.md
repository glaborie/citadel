    # ADR-014: Durable idempotency with honest semantics

    **Status:** Accepted  
    **Date:** 2026-11-23  
    **Last modified:** 2026-11-23

    ## Context

    Temporal retries activities, but a retried non-idempotent tool can duplicate effects. A short gateway dedupe window is not sufficient for side-effecting tools.

    ## Decision

    1. Every tool call carries idempotency_key = hash(run_id, workflow_step, tool_name, canonical_args).
2. Before a side effect, insert (key, status=pending) into Postgres with a unique constraint; on replay return the recorded result instead of re-executing.
3. Tool manifests declare idempotency support; T1/T2 tools without a key are hard errors.
4. Document the remaining crash window between effect and DB write as effectively-once, not exactly-once.

    ## Consequences

    - **Pros**: Retries and approvals cannot duplicate infrastructure changes; semantics are explicit rather than overclaimed.
    - **Cons**: Tool contract burden and one unavoidable failure window that must be disclosed.
