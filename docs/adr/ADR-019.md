# ADR-019: Secrets and supply-chain hygiene

**Status:** Accepted  
**Date:** 2026-11-23  
**Last modified:** 2026-11-25

## Context

A gitignored .env is acceptable for first development but not for real homelab credentials. The owner rejected LiteLLM on supply-chain grounds, so dependency policy belongs in the architecture.

## Decision

1. v0.1: gitignored .env plus .env.example with synthetic values only; no plaintext key in docs, skills, traces, audit or eval fixtures.
2. v0.2: SOPS + age becomes the source of truth for versioned/shared secrets; Compose injects runtime values via Docker secrets, not global env vars.

**Amended 2026-11-25 (issue #21):** Docker secrets are already used in v0.1 for
the values the Docker API made readable through `Config.Env` — the run-token
private key, the console session key, both GitHub tokens and the application DB
DSN. `make up` unwraps the SOPS file and `scripts/provision-secrets.sh` writes
them to gitignored files under `secrets/`, which Compose mounts as files; each
service reads `<NAME>_FILE` with the bare variable as the local fallback. The
socket proxy template also denies `/archive` and `/export`, because the pinned
image allows them while `CONTAINERS=1`. SOPS + age remains the v0.2 source of
truth.
3. v0.3: rotation procedure and leak scanning in CI.
4. Use uv.lock with hashes, pinned images, Dependabot/Renovate, pip-audit, Trivy and a clean-clone test.

## Consequences

- **Pros**: A credible security story from day one with a concrete migration path; no hidden-file dependency.
- **Cons**: SOPS/age migration is deferred work; scanning tools add CI time.
