# ADR-022: Agent approvers for T1 calls

**Status:** Accepted
**Date:** 2026-11-23
**Last modified:** 2026-11-26

## Context

ADR-009 makes T1 approval a human decision: the approver is a Keycloak user
holding the `approver` role, and an approver cannot approve their own request.
The owner wants a specialist agent to be able to approve a T1 call when
permission is granted, so routine remediation does not always wait for a human.

The risk is obvious: an agent that can approve its own action has no gate at
all. A prompt-injected Docker specialist could propose `restart_service` and
then approve it. Any design here must keep a separation of duties that a
compromised agent cannot collapse.

## Decision

1. Approval authority is a relation, not a role in prose: OpenFGA must grant
   `can_approve` on `tool:{tenant}/{tool}` to the approving agent
   (`agent:{tenant}/{agent}`). Without that tuple the agent cannot approve.
2. **Self-approval is impossible.** The approving identity must differ from the
   run's originating agent and from the user who requested the run. Enforced by
   the `approval.self_approval_denied` rule in the chokepoint, not by the UI.
3. T2 stays human-only with two distinct approvers. Agents never approve T2.
4. Human approval remains the default. Agent approval is opt-in per
   tenant/tool tuple and is visible in policy, not in a SKILL.md.
5. The audit event records actor type (`human` or `agent`), the approving
   identity, and the relation that authorised it, written before the Temporal
   resume signal.
6. An agent cannot grant itself `can_approve`; only an admin action on the
   policy store can.

## Implementation (2026-11-26)

- `policy/model.fga` defines `can_approve: [agent]` on `tool`. The bootstrap
  seeds no `can_approve` tuple, so every tool stays human-only until an admin
  writes one for a tenant/tool pair.
- `POST /approvals` accepts either credential: a Keycloak user token, or the
  approving agent's own short-lived run token. The run token is verified with
  the API's Ed25519 key and the agent identity is taken from its claims, never
  from the request body. An agent cannot present a user token and a human cannot
  present a run token; the two verifiers reject each other's signatures.
- `authorize_approval()` in `src/citadel/policy/authorize.py` is the chokepoint
  for the agent path: the tool must be in the catalog and T1, the approving
  agent must not be the run's originating agent, and OpenFGA must return
  `can_approve`. Any policy error denies.
- The four-eyes answer: **an agent may approve only a run proposed by a
  different agent.** The user who requested the target run is not a blocker for
  an agent approval in the common case, because both agents run on behalf of
  that same user and requiring another human would delete the autonomy this
  ADR exists to add. The separation is between the proposer and the approver,
  which is exactly the pair a compromised agent cannot be on both sides of. A
  human approver still cannot approve their own run.
- The audit event is `approval.decision` (the schema name; the issue's
  `approval.decided` describes the same event) with `actor_type=agent`, the
  audit column set to `agent`, and payload fields `actor_type`, `relation`
  (`can_approve` or `approver_role`), `approver` and, for an agent,
  `on_behalf_of` naming the user whose run the approving agent was started for.
  The existing Actor column in the run timeline and audit views renders it, so
  an agent approval is never mistaken for a human one.
- Red-team case `RT-HITL-07` proves an agent approving its own run is refused
  with `approval.self_approval_denied`.

## Consequences

- **Pros**: Routine, well-understood remediation can proceed without a human
  in the loop while remaining attributable and revocable; the gate becomes a
  policy tuple an interviewer can inspect.
- **Cons**: The `can_approve` tuple is now a privileged object and its
  compromise is equivalent to losing the human gate for that tool. The approval
  UI must render actor type so an agent approval is never mistaken for a human
  one. Adds a relation to the OpenFGA model and a rule to the chokepoint.
