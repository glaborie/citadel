# ADR-024: Approvals travel as a single-use reference, not a token in history

**Status:** Accepted
**Date:** 2026-11-25
**Last modified:** 2026-11-25

## Context

Temporal history holds the complete signal payload for every run: inputs, DLP
verdicts, tool output and the approval decision. It is replicated, exported,
backed up and read back through the Temporal UI, so anything in it is a
credential at rest. The approval was an Ed25519 JWT carried by the
`ApprovalDecision` signal, which made workflow history a store of bearer
credentials for T1 writes until expiry (issue #22).

Alternatives considered and rejected:

- **Publish the UI loopback-only.** Necessary, and done, but it covers one of
  the ways history is read, not the record itself (CLI, export, backup).
- **Shorten the TTL.** Bounds the leak window; does not stop the leak. Done as
  a second control.
- **Keep the signature and store the token outside history.** The signature was
  the authority, so any store the operator can read is readable by every
  component holding the same database role; the token would move, not go away.

## Decision

1. The approval decision stays in the append-only, hash-chained audit ledger,
   now carrying the argument hash and the approved TTL. The ledger is already
   the record a human-reviewed approval must produce.
2. The API signals only the audit event id. No approval token is minted and
   nothing in history is reusable as a credential.
3. The operator resolves the id under tenant RLS and requires: an
   `approval.decision` event, `decision = approved`, a named approver, matching
   run, tool and argument hash, and an unexpired TTL computed from the row's
   `created_at`. It consumes the id in `approval_tokens` before executing, so a
   second use is `409`. Unknown, denied, mismatched or expired ids are `403`.
4. The Temporal UI is published on `127.0.0.1` only and runs with
   `TEMPORAL_DISABLE_WRITE_ACTIONS=true`, so the console cannot terminate,
   signal or cancel a workflow.

## Consequences

- **Pros**: workflow history no longer contains a credential; a replay is
  refused by the same table that refused a replayed token; there is one fewer
  signing key on the approval path, and the approval record now names the exact
  argument hash it authorised.
- **Cons**: the ledger row becomes the authority for a T1 write. Anything that
  can INSERT an `approval.decision` event for a tenant can forge an approval,
  so the application database role and RLS are now part of the approval
  boundary that the Ed25519 private key used to hold alone. The migration is
  not backward compatible: `approval.decision` events written before this
  change carry no `args_hash` and resolve as unusable. A reference is still
  replayable until first use if it leaks, which the loopback-only UI and the
  shortened TTL bound.
