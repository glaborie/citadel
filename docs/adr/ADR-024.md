# ADR-024: Model-driven runs in the orchestrator workflow

**Status:** Accepted  
**Date:** 2026-11-25  
**Last modified:** 2026-11-25

## Context

The bounded agent loop (`citadel.model.run_agent`) and the OmniRoute client were built, typed and tested, and four red-team cases drove them. No runtime called them: `POST /runs` created a run row and a token, and a workflow only executed a named tool. Skill packs were hash-pinned and version-checked but never sent, so a "run" had a tool manifest and no prompt.

Two constraints shaped the wiring. The loop is synchronous and the workflow cannot await inline, so the loop had to become awaitable-tolerant. And the loop's `authorize` was argument-blind, which would have written a `policy.decision` with an empty args hash once the workflow started using it.

## Decision

1. `RunInput.prompt` selects a model-driven run. Without it the workflow keeps the existing single-tool path, which the drills and the tenancy tests use.
2. The loop stays one implementation. `run_agent` is `async` and awaits any awaitable callback, so tests and the red-team harness keep passing plain functions while the workflow passes activity-backed coroutines. `authorize` now takes `(tool, arguments)` so the policy decision records the real args hash.
3. The prompt is assembled by an activity from two existing authorities: the agent's hash-verified skill pack (index plus its references) and the tool catalog filtered to that agent. Neither grants anything; every requested call still goes through `authorize`.
4. Each callback is an activity on the queue that owns it: `complete`, `gate`, `system_prompt` and `tools` on the orchestrator; `authorize_tool` and `execute_tool` on the specialist's queue. Approval waits stay on the tool-driven path: the loop treats `requires_approval` as a denial.
5. Every completion writes one `model.call` audit row (alias, provider, model, input/output hashes, tokens, cost, latency), so the ordered run is gradeable and the gateway's own usage log joins back by run id.
6. `POST /runs` starts the workflow when a prompt is present, with the run id as the workflow id. If the start fails the API returns 503, marks the run failed and writes `run.end` with `workflow_not_started`, rather than reporting a start that did not happen.
7. The gated answer is recorded on `run.end` (bounded at 4000 characters); the prompt itself never enters the ledger, only its length and SHA-256.

## Consequences

- **Pros**: the same loop the unit and red-team suites exercise is the one the runtime executes; a trajectory now carries model calls, so token, cost and answer quality become gradeable; a prompt names hashed pack content rather than a label.
- **Cons**: a model-driven run cannot perform a T1 write, because approval waits are not wired into the loop; the budget is hardcoded in workflow code to stay replay-deterministic, so a tenant cannot yet set its own ceiling; and each turn costs two extra activities (prompt assembly is cached per run, not per turn).
