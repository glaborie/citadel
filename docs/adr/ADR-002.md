    # ADR-002: Temporal as the durable execution core

    **Status:** Accepted  
    **Date:** 2026-11-23  
    **Last modified:** 2026-11-23

    ## Context

    HITL gates, idempotency, recovery semantics and full-trajectory evaluation are properties of durable execution. A hand-rolled loop would require reimplementing all four, and the earlier Temporal POC was judged too simple to reuse.

    ## Decision

    1. Use self-hosted Temporal Server, Postgres, UI and workers inside Docker Compose.
2. Orchestrator and each specialist run as separate workflow types; specialist invocation uses child workflows so permissions, retries and history stay independent.
3. Approvals are implemented as Temporal waits resumed by signals/updates after an audit write.
4. Do not import, fork or copy the earlier Temporal POC.

    ## Consequences

    - **Pros**: Durable retries, resumable approvals, deterministic event history usable as trajectory datasets; clear separation of agent roles.
    - **Cons**: Extra containers and operational learning curve; Temporal's UI is not an approval UI and must not be used as one.
