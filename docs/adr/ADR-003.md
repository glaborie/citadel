    # ADR-003: Keycloak 26 for identity and delegated agent identity

    **Status:** Accepted  
    **Date:** 2026-11-23  
    **Last modified:** 2026-11-23

    ## Context

    Authentication alone is insufficient: the agent must act on behalf of a user with attenuated scope, and every tool call must be attributable to a user, tenant, agent and run.

    ## Decision

    1. Keycloak 26 issues user OIDC tokens with tenant claim and roles; it is the IdP for Citadel API, approval console and the proxy protecting MLflow and OmniRoute dashboards.
2. Each run receives a short-lived delegated agent token carrying user, tenant, agent, scopes, risk tier and run ID.
3. Select the exact RFC 8693 / identity-chaining mechanism at implementation time because Keycloak V2 exchange has documented caveats; the token shape and mandatory propagation are fixed here.
4. Downstream services reject tokens missing tenant or run ID.

    ## Consequences

    - **Pros**: Attribution, least privilege and a single place to revoke or rotate identity; interview-defensible answer to on-behalf-of execution.
    - **Cons**: Token plumbing is real work; Keycloak's identity-chaining caveats require verification before coding.
