OTLP trace ingestion (architecture §8) is verified against the docs:

- Endpoint is `/v1/traces`, header is `x-mlflow-experiment-id`.
- Requires MLflow >= 3.6.0, so the 3.18.0 pin satisfies it.
- **OTLP/HTTP only** — there is no OTLP/gRPC endpoint. The Python OTel
  exporter must be configured for `http/protobuf`; the gRPC default would
  silently fail to export.
- `X-MLFLOW-WORKSPACE` is available when workspaces are enabled.

Authentication has three viable shapes, and the design's "Keycloak OAuth2
proxy" covers only the human path:

1. Reverse proxy (`oauth2-proxy`) in front of MLflow. Matches the design
   literally. Authenticates browsers against Keycloak.
2. `mlflow-oidc-auth` plugin (Apache-2.0, v11.5.0, active). OIDC and RBAC
   inside MLflow, no extra container, but a third-party plugin needing a
   derived image and its own pin.
3. Built-in `--app-name basic-auth`. Local credentials, not Keycloak SSO —
   contradicts the design intent.

**Unresolved gap:** workers push traces to MLflow server-to-server over OTLP,
and a browser-session proxy cannot authenticate that push. The write path
needs a separate decision: internal-only route bypassing the proxy, a service
credential, or the OIDC plugin. This blocks the step 9 observability wiring,
not step 2.

## 3. gVisor availability

Resolved: `runsc` is **absent**. Docker runtimes are `runc`,
`io.containerd.runc.v2` and `nvidia`. Per ADR-012 the fallback is the
hardened sidecar without gVisor, which is what this host will run. The
Compose sandbox must therefore rely on `cap_drop: ALL`,
`no-new-privileges`, read-only rootfs, seccomp, resource limits and no
network by default.

**Refinement.** The daemon is **Docker Desktop** (`docker info` reports
`OperatingSystem=Docker Desktop`, `Name=docker-desktop`), not a native
`dockerd` in the Ubuntu WSL2 distro. The daemon runs in Docker Desktop's own
VM, so installing `runsc` into Ubuntu does not register a runtime with it.
gVisor here is not merely uninstalled — it is **not installable without
changing the Docker topology** to a native Docker Engine inside WSL2, and
gVisor on a WSL2 kernel is itself unverified. The ADR-012 fallback is
therefore the operating posture, not a temporary gap.

**Decision (2026-11-23): Path A**, keep the hardened-sidecar fallback and do
not change the Docker topology. This is the option ADR-012 already sanctions,
so no ADR amendment is needed. The upgrade path is documented, not applied, in
`docs/implementation-notes/docker-topology-upgrade.md`.

## 4. Compose skeleton facts

Verified by bringing the stack up from empty volumes.

- **OpenFGA's image is distroless** — no shell, no HTTP client, so it cannot
  carry a healthcheck. It also does not migrate on start; a separate
  `openfga-migrate` one-shot service must complete before `openfga` runs, or
  every `/healthz` probe returns 500 against a missing schema.
- **Temporal binds the container IP, not loopback.** A healthcheck against
  `127.0.0.1:7233` fails even while the server is serving; probe
  `$(hostname):7233` instead.
- **Docker cannot publish ports for a container attached only to an
  `internal: true` network.** Published services also need a non-internal
  network. Citadel therefore has `internal` (no route off the host) and
  `edge`; only `api`, `approval-ui`, `keycloak`, `temporal-ui` and
  `omniroute` sit on `edge`. Workers, the tool runner, Postgres, OpenFGA,
  Presidio and MLflow remain internal-only, and that is verified, not
  assumed: outbound requests from `worker-docker` and `tool-runner` fail.
- **Host ports 8000, 8001 and 8080 are already in use on this machine**, so
  Citadel publishes on its own range: api 18000, approval-ui 18001,
  temporal-ui 18080, Keycloak 18081, OmniRoute 20128.
- **OmniRoute serves the dashboard and `/v1` on the single port 20128.** Its
  own Compose file sets `API_PORT=20129` and `API_HOST=127.0.0.1` for a
  separate internal API; that is not the model gateway. The `.env.example`
  base URL is correct as written.
- **MLflow runs on SQLite** at `/mlflow/mlflow.db` with a named volume. The
  image carries no Postgres driver, so a Postgres backend would need a
  derived image; SQLite keeps the pin exact and satisfies the OTLP
  SQL-backend requirement. Upgrade path recorded for when concurrency
  matters.

## 5. Delegated identity (open item 4, resolved)

Keycloak 26.8.2 advertises `TOKEN_EXCHANGE`, `TOKEN_EXCHANGE_STANDARD_V2`
and `TOKEN_EXCHANGE_DELEGATION`.

**Standard token exchange V2** is GA (since 26.2) and was verified against
the running server, using only the committed realm file:

| Property | Result |
|---|---|
| `sub` (user identity) | preserved across the exchange |
| `tenant` claim | preserved |
| `realm_access.roles` | preserved |
| `aud` | narrowed to `citadel-agent` |
| lifetime | 300 s |
| unauthenticated exchange | rejected, 401 `unauthorized_client` |
| `run_id`, `agent`, `scopes`, `risk_tier` | **absent — cannot be carried** |

V2 requires the requesting client to appear in the subject token's `aud`,
which the `citadel-audience` scope provides. It needs no fine-grained admin
permissions.

**RFC 8693 delegation (`may_act`) was rejected.** It is preview, needs
`token-exchange-delegation` plus `parameterized-scopes`, needs FGAP V2
`delegate` permissions, and requires `Consent required` on the client with
consent **never stored permanently** — the user re-approves on every login
session. That is unusable for an autonomous agent run.

**Decision.** Citadel verifies the Keycloak user token against JWKS, then
mints its own short-lived run token carrying user, tenant, agent, scopes,
risk tier and run ID. This is the implementation-time choice ADR-003
explicitly delegates; the token shape and mandatory propagation are
unchanged. Run tokens are **Ed25519**: the API holds the private key and
mints, workers hold only the public key and can verify but never forge.

### Realm and database traps found while verifying

Each of these silently produced a working-looking but insecure setup:

1. **`defaultDefaultClientScopes` naming undefined scopes drops them.** The
   first import listed `basic` and `roles` without defining them, so no
   `sub` and no `realm_access` ever appeared. Both scopes are now defined
   explicitly in the realm file.
2. **The declarative user profile silently discards undeclared attributes.**
   Setting `tenant` on a user did nothing until `tenant` was declared as a
   required, admin-managed attribute. Without this every user would fail
   closed forever.
3. **`fullScopeAllowed: false` drops realm roles** unless they are granted
   through `scopeMappings`. The realm file now grants operator/approver/viewer.
4. **`POSTGRES_USER` is a superuser and superusers bypass RLS entirely.**
   The app connects as `citadel_app`, a `LOGIN NOBYPASSRLS` role created by
   `docker/postgres/init/02-app-role.sh`. Verified: `rolsuper=false`,
   `rolbypassrls=false`.
5. **Issuer and JWKS URL must be separate.** `KC_HOSTNAME` pins the issuer to
   `http://localhost:18081`, while the API fetches keys over
   `http://keycloak:8080`. Deriving the JWKS URL from the issuer would make
   the API unreachable from inside the network.
6. **A CRLF `.env` breaks Compose values.** Keycloak rejected the bootstrap
   admin password until `.env` was normalised to LF.

### Verified behaviour

`tests/test_tenancy_live.py` (run with `CITADEL_LIVE_TESTS=1`) proves against
the live stack: a run created by alice in `lab-a` is invisible to bob in
`lab-b`; an unset `app.tenant_id` returns zero rows rather than all rows;
and `citadel_app` cannot bypass RLS. Hermetic tests cover forged signatures,
expired tokens, missing tenant claims, wrong issuer/audience, an unreachable
key source, and a worker holding only the public key being unable to mint.

### Credential exposure found and fixed

`KEYCLOAK_ADMIN_PASSWORD` in `.env` was still the literal placeholder

Lesson for the remaining steps: a placeholder that is *accepted* by a
service is worse than a missing value, because nothing fails loudly. Any
future bootstrap credential must be checked against the placeholder string,
not merely checked for presence.

## 7. Policy chokepoint (step 4)

The OpenFGA model lives in `policy/model.fga` and is the source of truth.
`policy/model.json` is generated from it by `make policy-model` and committed,
so the api image never needs the OpenFGA CLI. Four types:

| Type | Relations |
|---|---|
| `user` | — |
| `tenant` | `member` |
| `agent` | `tenant`, `invoker` = direct user or `member from tenant` |
| `tool` | `tenant`, `agent`, `can_call` = direct user or `invoker from agent` |

A tool with no `agent` relation is callable by nobody, so an unwritten tuple
denies by default.

`citadel.policy.authorize()` is the single chokepoint. Rules, in order:

1. missing tenant, user, run or agent → deny
2. tool absent from the catalog → deny
3. T2 → deny, **before** any relationship lookup
4. requesting agent ≠ owning agent → deny
5. policy service error or unreachable → deny
6. OpenFGA says no → deny
7. T1 and allowed → `requires_approval`
8. T0 and allowed → allow

### Findings while wiring it

- **OpenFGA object ids cannot contain `:`.** `agent:lab-a:docker` is rejected
  with `invalid 'object' field format`. Object ids are `type:id` and the id
  segment is a single token, so tenant scoping uses `agent:lab-a/docker` and
  `tool:lab-a/read_logs`.
- **The sync client is imported from `openfga_sdk.sync`**, not
  `openfga_sdk.sync.client`; the latter package has an empty `__init__`.
- **`write_authorization_model` takes a request object**, not kwargs.

### Gap found and closed

`/policy/authorize` originally trusted the supplied `run_id` for audit
without checking ownership. A caller could cite another tenant's run. The
endpoint now resolves the run inside the caller's tenant through the same RLS
connection, so a foreign run id is simply not found and the decision is
`identity.unknown_run`.

### Verified against the live stack

| Case | Outcome | Rule |
|---|---|---|
| alice, `read_logs`, own run | allow | `policy.allowed` |
| alice, `restart_service` | requires_approval | `policy.tier_requires_approval` |
| alice, `delete_volume` (T2) | deny | `tool.tier_denied` |
| alice, unlisted tool | deny | `tool.unknown` |
| alice, docker agent asking for `search_code` | deny | `tool.agent_mismatch` |
| bob, alice's `run_id` | deny | `identity.unknown_run` |
| alice, no `run_id` | deny | `identity.missing_run` |

The tenant is never client-supplied: an extra `tenant_id` field in the body
is rejected with 422 by `extra="forbid"`.

## 9. Temporal path (step 5)

Three workers poll three task queues: `orchestrator`, `docker`, `github`. The
orchestrator owns no side-effecting tools and only delegates
(`RunWorkflow` -> `SpecialistWorkflow` child workflow).

**Approval wait/resume.** A T1 call parks in `workflow.wait_condition` for the
15-minute TTL. Signal `approve(ApprovalDecision)` resumes it. No signal by
deadline raises `TimeoutError` and returns `approval.expired` — expiry is an
automatic deny, never an implicit approval.

The child workflow id is `run-{run_id}-{tool}`, so the approval console can
signal by convention without a lookup table.

**Idempotency.** The key is
`sha256(canonical json({tool, arguments}))` prefixed with the run id. The
`execute_tool` activity inserts into `tool_calls` with a unique constraint and
`ON CONFLICT DO NOTHING`; when the insert returns no row the stored result is
replayed instead of repeating the side effect. Effectively-once, not
exactly-once: a crash between commit and acknowledge still replays the stored
result, which is the honest guarantee from ADR-014.

**Sync activities need an executor.** Policy and psycopg are synchronous, so
`Worker(activity_executor=ThreadPoolExecutor(...))` is mandatory. Without it
Temporal raises `Activity ... is not async so an activity_executor must be
present` at worker start, and a mis-scoped executor fails with
`cannot schedule new futures after shutdown` at the first task.

### Verified live

| Case | Result |
|---|---|
| orchestrator -> docker child, T0 | `executed` / `tool.executed` |
| same run, tool and arguments again | `replayed` / `idempotency.replayed` |
| T1 before any signal | workflow `RUNNING`, parked on the approval condition |
| T1 after `approve` signal | `executed` / `tool.executed` |

8 hermetic workflow tests use Temporal's time-skipping environment, so the
15-minute TTL is exercised instantly, and cover policy deny, T0, T1 approve,
T1 deny, TTL expiry, retry-then-succeed, and key stability across argument
ordering.

### Known limit

The child workflow id is `run-{run_id}-{tool}`, so a *second* call of the same
tool inside one run would collide instead of starting a new child. v0.1 runs
one tool call per run; when a run fans out, the id needs a sequence or the
idempotency digest appended.

## 10. Tool invocation and audit ledger (step 6, partial)

**Tool invocation.** The model never supplies a command line. It supplies a
tool name and named arguments; `build_argv` renders them against the catalog's
declared parameters and then re-checks the result against the command
allowlist. The two layers do different jobs: the catalog decides which tools
may be *authorisable*, the allowlist decides which command lines may *exist*.

Denied at this layer: unknown tool, tool with no `command` mapping, T2 tool,
missing required argument, unexpected argument name, non-string value,
over-long value, and any value containing shell metacharacters.

**Output-risk caveats live in `commands.json`**, not only in prose.
`content_risk: "definitive"` means the command discloses secrets by design —
currently `docker.inspect` (dumps `.Config.Env`) and `docker.compose.config`
(prints the interpolated file with `.env` values). `"possible"` marks
`docker.compose.logs`, `gh.pr.diff`, `gh.pr.view` and `gh.issue.list`, where
secrets can appear in normal content.

The distinction is **enforced**: a test asserts no catalog tool maps to a
`definitive` command, so those two cannot reach a model before the DLP wrapper
redacts their output.

**Audit ledger.** Append-only, hash-chained per tenant in `audit_events`.
Each hash covers `prev_hash | tenant | seq | event_type | actor_type |
actor_id | payload`, and appends are serialised per tenant with
`pg_advisory_xact_lock`. `citadel_app` holds INSERT and SELECT only; UPDATE and
DELETE are absent, verified live as `false,false,true`.

### Bug found by the tamper test

The first version hashed everything except `actor_type` and `actor_id`.
Rewriting `actor_id` to `attacker` left `verify()` returning `(True, 3)` —
actor spoofing was invisible. Both fields are now in the material, and a
tampered row yields `(False, 3)` against the live database.

That is worth keeping in mind for the rest of the audit work: a hash chain
only proves what is inside the hash, and the obvious omission is exactly the
field that identifies who did it.

### Not done yet

Tool *execution* — the socket proxy for T0 Docker reads and the operator
service for T1 — remains blocked on ADR-023. Audit events are written for
policy decisions; tool-call and approval events arrive with the executor.

## 11. Sandboxed tool execution (step 6, T0 path)

ADR-023 accepted. Tool execution now runs end to end:
Temporal -> policy chokepoint -> command allowlist -> sandbox -> read-only
Docker proxy -> host daemon.

**Network split.** `docker-socket-proxy` sits on a dedicated `sandbox`
network shared only with `tool-runner`. The proxy is deliberately *not* on
`internal`, so no other service can reach the Docker API. `tool-runner` is on
both, which makes it the only bridge — and that is a widening versus the old
`network_mode: none`, stated plainly: the sandbox can now reach internal
services even though it has no route off the host.

**Proxy surface.** `CONTAINERS=1` and `POST=0`; images, networks, volumes,
exec, build, swarm and secrets are all off. Verified from inside the sandbox:
`GET /containers/json` -> 200, `POST /containers/x/restart` -> 403,
`POST /containers/create` -> 403, `DELETE` -> 403.

**The sandbox re-validates.** `tool-runner` does not trust the worker: it
rebuilds the argv from the catalog, re-checks the allowlist, refuses a
mismatched agent, and refuses any command whose `content_risk` is set. It
execs with `shell=False`, a 30 s timeout, a 64 KB output cap and an
environment whitelist (`PATH`, `DOCKER_HOST`, `HOME`) so nothing ambient
reaches the child.

### Findings while wiring

- **The proxy needs writable `/tmp` and `/run`.** With `read_only: true` its
  entrypoint fails twice: first rendering `haproxy.cfg`, then writing the
  pidfile. Two tmpfs mounts fix it.
- **The app image had no `docker` binary**, so the first sandbox call would
  have died on `FileNotFoundError`. The CLI is now copied from a pinned
  `docker:29-cli` stage.
- **There is no public `gh` image** at `ghcr.io/cli/cli` or `cli/cli`. `gh` is
  therefore not installed, and the sandbox returns a clean 503 instead of a
  500 when a command's binary is missing.

### Verified end to end

| Case | Result |
|---|---|
| workflow `inspect_containers` | `executed`, allowlist `docker.ps`, `docker ps` output from the host daemon |
| `read_logs` | 403 — `content_risk` blocks it until DLP |
| `get_pr_status` as the docker agent | 403 — agent mismatch |
| proxy write attempt | 403 on POST and DELETE |
| `tool_calls` row | records `inspect_containers`, `executed`, `docker.ps` |

### Resolved later in step 6

- **T1 `restart_service`** — the operator service from ADR-023 item 3, §12.
- **GitHub** — the PAT, the allowlisted egress path and `gh` in the sandbox,

## 12. Operator service (step 6, T1 path)

The sandbox is read-only by construction, so T1 writes needed a second writer.
`operator` is that component: it holds the Docker socket and the GitHub write
token, performs only the two T1 actions in the catalog, and accepts no command
line — the argv is rebuilt from the catalog on every call.

**Approval tokens.** The API mints an Ed25519-signed token after a human
approves, binding `tenant | run_id | tool | sha256(arguments)` plus a `jti`.
The token carries `typ: approval` and `aud: operator`, so a run token replayed
as an approval is rejected on the type claim rather than on luck. Single use is
enforced by a `approval_tokens` table with `jti` as the primary key.

**Separation of duties.** `/approvals` requires the `approver` role, refuses a
run the caller requested, writes the audit event *before* signalling Temporal,
and only mints a token when the decision is `approved`.

**The operator itself** re-builds the argv from the catalog, refuses anything
not T1, maps `service` to the Compose container name for `docker restart`, and
runs `gh pr create` for `open_remediation_pr` (§14). The sandbox refuses T1
outright, so the split is enforced on both sides.

### Verified live

| Case | Result |
|---|---|
| alice approves her own run | 403 |
| carol approves, workflow resumes | `executed`, allowlist `docker.restart`, exit 0 |
| container restarted | `citadel-approval-ui-1` StartedAt moved to the run time |
| audit chain after approval | `(True, 7)` |
| approval token reused | 409 |
| same token, different service | 403 `approval does not match these arguments` |
| approval without a token | `approval.missing_token`, no execution |

### Known limits

- The operator mounts the Docker socket directly. It is not model-influenced,
  but if it were compromised the socket is full control. The proxy split
  protects the sandbox, not the operator.
- `open_remediation_pr` carries caller text (title and body): the one place
  model-influenced content reaches a write. The approval token hashes the exact
  argument set, so a human approves the words that are posted.
- `container_name()` assumes Compose naming (`citadel-<service>-1`), so it
  breaks if the project name changes.

## 13. GitHub egress and the sandbox CLI set (step 6, GitHub path)

Workers have no egress, so `gh` runs in the sandbox and its traffic goes
through one door.

**Egress proxy.** Squid with a `dstdomain api.github.com` allowlist, reachable
only on the internal network. Verified from inside the sandbox:
`https://api.github.com/zen` -> 200, `https://example.com/` -> 403,
plain `http://api.github.com/zen` -> 403. `gh` uses the GraphQL endpoint on
the same domain, so one rule covers both.

**Per-role images.** The Dockerfile now has three targets so a CLI cannot leak
into the wrong container: `app` (api, approval console, workers) has no CLI at
all, `operator` has docker only, `sandbox` has docker and gh. `gh` is pinned at
2.105.0 and verified against the published sha256 at build time.

**Per-binary environment.** `GH_TOKEN` — the variable `gh` itself reads — is
only exported to `gh`; `docker ps` cannot read it. It is filled from a secret
named for its purpose: the sandbox maps `GH_READ_TOKEN` to `GH_TOKEN`, and
`GH_WRITE_TOKEN` is reserved for the operator and never appears in the sandbox
environment. `HTTPS_PROXY` is set so every HTTPS call goes through the
allowlist.

### Findings

- **Squid would not start under `cap_drop: ALL`.** Its entrypoint drops
  privileges with `setgid`, which needs CAP_SETUID/CAP_SETGID. That service
  keeps default capabilities and is documented as the one exception; its only
  reachable destination is api.github.com.
- **Custom `access_log`/`pid_filename`/`cache_log` paths made squid exit 1**
  with no message. Using the image defaults and only overriding the ACLs works.
- **`HTTP_PROXY` captured loopback calls.** urllib sent
  `http://127.0.0.1:8020/execute` to the proxy, which returned an HTML 403.
  `NO_PROXY`/`no_proxy` now cover localhost, 127.0.0.1 and the Docker proxy, or
  every internal call from the sandbox would break.

**Token scope is deliberate.** The sandbox token is read-only (a PR-create
probe returns 403 `Resource not accessible by personal access token`) but it
covers a chosen mix of public and private repositories, including the private
`citadel` repo. The owner confirmed this is intentional: the specialist needs
to read its own infrastructure repositories. The write path still lives
elsewhere, so read-only is the property that matters.

Note for anyone re-checking this: the `permissions` field on a repo response
reports the *authenticated user's* role, not the token's scope. An owner sees
`admin:true, push:true` even for a read-only token. Probe with a write attempt
instead, and expect 403 rather than 422.

### Verified with no token

`get_pr_status` for `cli/cli` ran as allowlist `gh.pr.list`, exited 1 and
reported `HTTP 401: Bad credentials (https://api.github.com/graphql)`. That is
the correct failure: the command ran, the tunnel opened, GitHub answered.

## 14. T1 `open_remediation_pr` (step 6, GitHub write path)

The tool opens a *draft* PR from a branch that already exists. The operator
does not create commits, so no code content crosses the boundary: the proposed
change is whatever that branch contains, and the PR is the request to review
it.

**Shape.** `gh pr create --draft --repo R --base B --head H --title T --body X`.
`--draft` is fixed in the allowlist argv prefix, so an un-drafted PR cannot be
requested. `--fill` was the first choice, because it would have kept caller text
out of the operator entirely; it needs a git checkout of the branch, so it was
dropped. The title and body are therefore caller text, and that is safe because
the approval token hashes the exact argument set: the operator can only post the
words a human approved, and changing one character fails verification.

**Images.** The operator target carries `gh` 2.105.0 and `git`. `git` is not used
for a checkout; `gh pr create` shells out to it even when `--repo`, `--base` and
`--head` are all explicit. `git` is not in the command allowlist, so the
operator cannot run it directly.

**Token split, exercised.** `GH_WRITE_TOKEN` is mapped into the operator as
`GH_TOKEN` and appears nowhere else; the sandbox still gets `GH_READ_TOKEN`.

### Verified live

| Case | Result |
|---|---|
| sandbox asked for `open_remediation_pr` | 403 `gh.pr.create is T1; use the operator service` |
| carol approves, run executes | `executed`, allowlist `gh.pr.create` |
| request reached GitHub | GraphQL `createPullRequest`: `No commits between main and <branch>` |
| approval token reused | 409 |
| same token, different head branch | 403 |
| a T0 tool sent to the operator with a valid token | 403 `docker.ps is not a T1 command` |

The GraphQL error is the positive signal: the mutation was parsed and rejected
on content, which only happens after the token's permission check passed. A
missing `Pull requests: write` returns `Resource not accessible by personal
access token` instead.

### Known limits

- **The branch must exist.** The agent chooses the repo, base, head and the PR
  text, but not the diff; preparing the change stays a human or CI step.
- Title and body are single-line and may not contain `..` or shell
  metacharacters, because the allowlist matcher rejects those tokens. An
  ellipsis in prose is refused. The upgrade is a checkout plus `--fill`, which
  needs a workspace inside the operator.
- **No PR was actually opened during verification.** The drill used a branch
  that does not exist, so proving the path published nothing.

## 15. Retry semantics for tool calls (step 6)

`RetryPolicy` was decorative: `_post` caught `OSError` and every `HTTPError`
and turned them into a `failed` `ToolResult`, so the activity always returned
normally and Temporal never retried. One DNS blip ended a run.

**The split now.** HTTP errors are results, transport failures are exceptions.
A service that answered is deterministic — retrying the same request gets the
same answer, and for a write it could repeat a side effect. A service that
never answered is exactly what retries are for.

**The `sent` marker.** Making retries real exposed the question the retry has
to answer: did the earlier attempt reach the tool? `execute_tool` now commits
`status = 'sent'` *before* the request leaves the process, in its own
transaction, so a crash cannot roll the marker back.

| Row status | Read (T0) | Write (T1) |
|---|---|---|
| `executed` / `replayed` / `failed` | replay stored result | replay stored result |
| `sent` | attempt again | `tool.possibly_executed`, do not attempt |
| none | attempt | attempt |

A `sent` write is the one genuinely unknown outcome. It is reported, never
guessed: the approval token is already consumed, so the command may have run.

**Retries exhausted.** The specialist catches `ActivityError` and returns a
`tool.no_result` failure, so an outage produces a recorded result instead of a
child workflow that dies without one.

### Verified live

Stopped `tool-runner`, then ran `get_pr_status` for `cli/cli`:

| Observation | Value |
|---|---|
| workflow result | `failed`, rule `tool.no_result` |
| history | `ACTIVITY_TASK_FAILED` with `retry_state = MAXIMUM_ATTEMPTS_REACHED` |
| `tool_calls` row | `sent`, result empty |
| after restarting the sandbox | exit 0, 30 PRs |

The `sent` row is the marker doing its job: it is what a later attempt reads to
know the call left the process. The same drill on the previous image wrote
`status = 'failed'` after a single attempt, which is the bug this replaces.

### Known limits

- A `sent` T1 row is permanently "unknown". Nothing reconciles it: a human has
  to check whether the restart or PR happened. Automatic reconciliation would
  need the operator to record the command's outcome against the `jti`.
- A retried read repeats the call. `gh pr list` is harmless; a read that is
  expensive or rate-limited is not free.

## 16. DLP wrapper (step 7)

The sandbox refused every `content_risk` command because nothing redacted output
before it was served. That is now a control rather than a refusal.

**Two layers, deliberately.** Presidio finds PII it has been trained for. It
cannot find credentials — a `ghp_` token is random characters, not a name — so a
deterministic rule set runs beside it and wins arguments. The hard rules
override the detector, and each override records what the detector said:

| Layer | Finds | Action |
|---|---|---|
| Presidio | emails, phones, cards, IBANs, public IPs, SSNs, crypto addresses, AHV | redact |
| Hard rules | GitHub/Slack/AWS/age tokens, private-key headers, bearer tokens, connection strings | block |
| Hard rules | AHV (`756.…`) | redact |

**Two surfaces, two rules.**

| Surface | Anything found | Why |
|---|---|---|
| input | block | Redacting an argument would run a command other than the one policy authorised — and, for a T1 write, other than the one a human approved. |
| output | secrets block, PII is redacted in place | The command already ran; the text is what must not leave. |

The gate sits in the runner and the operator, not in the worker, so a
compromised worker cannot skip it. Both services return one report per surface,
passes included, and `execute_tool` appends them as `dlp.event` rows. A pass is
recorded because "the control ran and found nothing" is the evidence; an absence
of rows would prove nothing.

**Fail closed.** Detector unreachable, timed out, non-JSON or not a list raises
`DlpUnavailable`. The tool service answers 503 with `reason: dlp_unavailable`,
and the activity records `dlp.unavailable`. There is no path where unchecked
text is served.

### Custom recognizers

Presidio's `ad_hoc_recognizers` supports pattern recognizers per request, so the
AHV recognizer travels with every call and is versioned in the repo instead of
being registered at container start. Verified against the running analyzer:

| Sample | Result |
|---|---|
| `756.1234.5678.97` | `AHV` 0.90 (our recognizer) |
| `CH9300762011623852957` | `IBAN_CODE` 1.00 (native, so no custom Swiss-IBAN rule) |
| `ghp_…`, `AKIA…`, `-----BEGIN RSA PRIVATE KEY-----` | nothing — the detector does not see credentials at all |

That last row is why the hard-rule layer exists, and the live block below shows
it reporting `detector_verdict: missed`.

### Two calibration findings

Both were found by running the thing rather than by assuming it worked.

1. **`PERSON` redacted `docker`.** Presidio scored `docker` in
   `docker: unknown command` at 0.85 — identical to `Alice Smith` — turning the
   error into `<PERSON>: unknown command: <PERSON> compose`. `PERSON` is not
   requested in v0.1; free-text names are an open item, structured identifiers
   are not.
2. **`IP_ADDRESS` redacted bind addresses.** Every `0.0.0.0:18000->8000/tcp` in
   `docker ps` scored 0.6. Only global addresses are redacted now; loopback,
   wildcard and RFC1918 are the environment, not personal data.

### Known limits

- **`read_logs` still cannot run.** DLP is no longer the blocker, but the
  allowlist maps it to `docker compose logs`, and the sandbox has neither the
  compose plugin nor a compose project file: `docker: unknown command: docker
  compose`, exit 1. The output was redacted correctly; the command is wrong.
- **T1 arguments reach the approval UI before the gate sees them.** The operator
  blocks execution, but the console renders the argument values that a human is
  being asked to approve. Moving the check to approval-request time needs a new
  activity; it is an open item.
- **English only.** Presidio's NER models are per-language.
- **Latency is real.** 64 KB of log text took 6.3 s and produced 727 entities on
  this host; the analyzer timeout is 30 s.
- **A no-detector run is refused, not queued.** A presidio outage fails the
  call; nothing retries a DLP decision.

## 17. `read_logs` runs `docker logs` (step 7 follow-up)

Step 7 unblocked `read_logs` at the DLP gate, and it still could not run: the
allowlist mapped it to `docker compose logs`, which the sandbox cannot execute.

| Observation | Value |
|---|---|
| before | exit 1, `docker: unknown command: docker compose` |
| cause | the sandbox image has no compose plugin, and no compose project file to read |
| now | `docker logs citadel-<service>-1` |

**The derivation moved down.** `restart_service` resolved `service` to
`citadel-<service>-1` in the operator. `read_logs` needs the same translation, so
it now happens in `build_argv`, which both the sandbox and the operator call. The
approval token still binds the original service name: resolution happens after
verification, and the derived argv is what gets validated — a value that would
fail the normal checks is passed through untouched, so it is refused by the same
code and with the same message.

`--follow` is deliberately not allowlisted: it would hold the call open until the
sandbox timeout. `--details`, `--timestamps`, `--tail`, `--since` and `--until`
are.

|---|---|
| sandbox direct, `read_logs` on `api` | exit 0, real log lines, three DLP passes |
| through Temporal | `executed`, detail `read_logs executed as docker.logs` |
